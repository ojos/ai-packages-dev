## v0.2.0

### Summary
- **破壊的変更。第二意見レビューの雛形を `templates/gemini-review.sh` から `templates/second-opinion-review.sh` へ改名した**（issue #268）。認証手段の異なる 2 つの CLI から選べるようになったため、エンジン名を含む名前が事実と合わなくなった。**旧名の shim は残していない**（下記「移行」）。
- **第二意見のエンジンを選べるようにした**（issue #268）。`--engine gemini|antigravity`。既定は `gemini` 据え置きで、指定しなければ挙動は変わらない。`antigravity`（Antigravity CLI `agy`）は Google アカウントの OAuth 認証で、API キーに対応しない。API キーのクォータ切れや失効がそのままゲート停止になる状態を解消する。
- **第二意見の通過判定を「出力の最後の行に置かれた判定トークン」へ変更した**（issue #267。**挙動変更**）。モデルが回答の前に作業ナレーションを 1 行出すだけで、指摘が 1 件も無くても「指摘あり」に分類され、ローカル事前ゲートが偽の赤を返していた。**`--runs` を増やしても回避できない**（実測では 3 run すべてが同じ形で落ちた）。
- **環境変数を `SECOND_OPINION_*` へ改めた**（issue #268）。旧名 `GEMINI_REVIEW_RUNS` / `GEMINI_REVIEW_MODEL` も後方互換で受理する（新名が優先）。
- **受け入れ条件を二層（ローカル層 / 外部層）へ分ける規範を追加した**（issue #244）。反復のたびに回す機械判定と、外部認証やネットワークを要する検証を分け、**ループの接地信号はローカル層のみ**とする。`loop-workflow.md` に節を新設し、`templates/project-ai-rules.md` へ記入欄を置いた。
- **リモート最終ゲートの確認側 `templates/review-gate.yml` が、進行中のレビューを「要求されていない」と誤判定する不具合を修正した**（issue #235）。レビュアーはレビューを開始した時点で `requested_reviewers` から消え、投稿するまで `reviews` に現れない。この 2 つしか見ないと、その窓で failure になる。timeline を見て判定する。
- **`role-contracts/closer.md` に、マージ実行へ確認を挟む機構の担保を追記した**（issue #241）。「既定の merge 方針は手動承認とする」は呼びかけだけでは破れる（実運用で承認を経ないまま PR 2 本がマージされた実例がある）。
- 雛形は **6 種**のまま（`gemini-review.sh` が `second-opinion-review.sh` へ改名。増減なし）。

### Highlights

- **判定を出力全体の一致で行ってはいけない（#267）**: モデルの前置き（作業ナレーション）は同じ差分なら毎回同じように出るため、多数決では消えない。偽の赤が定常化するとゲートそのものが読まれなくなる。**却下の手順も使えない** — 却下は事実誤認の指摘を人が退ける規則だが、このときは却下すべき指摘そのものが存在せず、分類が誤っている。
- **かといって「LGTM を含む」へ緩めない（#267）**: ファイル別に講評して途中の 1 行へ `LGTM` と書く形や、指摘の末尾へ `**LGTM**` を添える形は、モデルが自然に取る出力で実際に起きる（v0.1.7 で塞いだ穴）。判定トークンを `VERDICT:` 付きの専用の形にすることで、前置きを許しつつこの穴を開けない。**判定トークンの無い出力は指摘あり扱い**とし、指摘本文と区別できる診断を出す。
- **構造化出力では前置きを分離できない（#267。実測）**: gemini CLI 0.53.1 の `-o json` を実測したところ、`.response` にツール呼び出し前の本文がそのまま含まれていた。「判定を構造化出力へ移す」案は成立しない。
- **判定ロジックはエンジン間で複製しない（#268）**: 2 本のスクリプトを並置すると、判定の修正が片側にしか効かない状態が生まれる。1 本へ統合し、エンジンごとに違うのは **CLI 名・認証・差分の渡し方の 3 点だけ**に閉じた。
- **差分の渡し方はエンジンごとに実測して決めた（#268）**: `agy` は `@<パス>` をファイル参照として展開せず、print モードで標準入力も読まない。したがって差分はプロンプトへ直接載せ、引数長の上限を手前で検査して止める（黙って切り詰めない）。gemini 側は従来どおり一時ファイル + `@` 参照（v0.1.7 で塞いだ `@` 展開事故の対策を維持）。
- **回答が空でも終了コード 0 になる経路がある（#268。実測）**: 非対話の `agy` はツールの実行許可を自動拒否し、「回答なし」を stderr へ書いて 0 で終える。判定は指摘あり側へ倒れるが画面には何も出ないため、CLI の診断をそのまま見せる。

### 移行

**取り込み済みの利用側は、次の 3 つが必要です。**

1. **雛形の再取得と旧名の削除。** `templates/second-opinion-review.sh` を `scripts/` へコピーし、`scripts/gemini-review.sh` を削除する。
2. **呼び出し側の差し替え。** `LOOP_GATE_REVIEW_CMD` でコマンドを固定している場合は新しいパスへ。未設定なら、`loop-gate.sh` の再取得（DCB v0.9.1 以降で生成）だけで足りる。
3. **`.env` のキー名の移行。** `GEMINI_REVIEW_RUNS` → `SECOND_OPINION_RUNS`、`GEMINI_REVIEW_MODEL` → `SECOND_OPINION_MODEL`。実装は旧名も受理するが、**機密混入検査（`check-no-secrets.sh`）が「`.env` にあるキーが `.env.example` に無い」を `SECRETS_FAIL` として出す**ため、旧名を残したまま新しい雛形を取り込むとゲートが落ちる（実測）。

`--engine` を指定しない限り、レビューの実行系（gemini CLI + API キー）は従来どおりです。判定は変わります（前置き付きの出力が通るようになり、判定トークンの無い出力は落ちます）。

## v0.1.8

### Summary
- **リモート最終ゲートが要求されないまま PR が通る穴を塞いだ**（issue #222）。`pull_request` の `opened` は GitHub 側の配信取りこぼしで届かないことがあり、届かなければ自動要求のワークフローは起動せず、エラーも出ず、他のチェックは緑になる。**最終ゲートだけが黙って抜ける。** 要求されたことを別の契機で確認する雛形 `templates/review-gate.yml` を新設し、規範へ「要求されたことを別の契機で確認する」節を追加した。
- **`templates/copilot-review.yml` に要求失敗時の診断を追加した**（issue #222）。素の 422 だけでは「所有者側でレビュー機構が無効」なのか「トークン権限不足」なのかが PR 上から判別できず、放置される。失敗を握り潰してスキップにはしない。
- **指摘が事実誤認だった場合の扱いを規範へ定めた**（issue #226）。「解決済みとして扱ってよい」条件は CI 通過 / スコープ外 / 命名・可読性の好みの 3 つしかなく、事実誤認の指摘を却下する根拠が無かった。条件と、却下時の記録要件を「指摘の却下」節として追加した。
- 雛形は 5 種から **6 種**になった。規範の追加のみで後方互換。

### Highlights

- **`opened` を見る 2 本目のワークフローでは塞げない（#222）**: 届いていないのはイベントそのものなので、同じ契機を見る側も同じように起動しない。**別の契機が要る**というのが `review-gate.yml` の設計上の核で、要求側と同じ契機に加えて PR 更新（`synchronize` 等）と**定期実行**を張る。定期実行は「開いたきり触っていない PR」を拾う最後の担保。実運用では、連続する 2 日間に開いた 6 本の PR のうち 2 本でこの取りこぼしが起きている。
- **確認側は要求しない（#222）**: 確認側も要求すると、規範の「1 回だけ要求する」が 2 か所から壊れる。要求と確認は別の機構に分ける。
- **判定は head コミットの status として出す（#222）**: ジョブの成否だけでは、定期実行から見た PR に何も現れない（その実行が PR に紐づかないため）。status にすれば、どの契機から判定しても同じ場所に出る。
- **確認できなかったことを「要求されていない」と同じに扱わない（#222）**: 一時的な不調で赤が出る。逆に握り潰して緑にすると、確かめていないものを通したことになる。判定を保留し、次の契機へ持ち越す第 3 の答えを持つ。
- **required check にはしない（#222）**: レビュー機構側の遅延や障害でマージが止まる副作用がある。ここで止めたいのは「要求されていないことに気づかないまま通ること」だけ。
- **却下の根拠が無いと、採れる手が 3 つに限られる（#226）**: 存在しない不具合の修正を入れる（実測と矛盾する説明がコードに残る）、ゲートを迂回して通す（通したのか迂回したのか区別できなくなる）、指摘が出なくなるまで再実行する（非決定性に賭けるだけ）。いずれも規範の意図に反する。
- **条件だけを足すと抜け道になる（#226）**: 「事実誤認だから」を主張だけで通せるようにすると、条件がそのまま抜け道になる。再現手順と実測結果を残さない却下を認めない。あわせて、指摘が述べる故障モードが起きないことに加えて**同じ位置で実際にそれが起きる条件（対照）**も示すことを求める。「起きなかった」だけでは、確かめ方が間違っていた可能性を排除できない。
- **却下と採否は別（#226）**: 指摘の前提が誤っていても、指摘が示唆する対処には価値がある場合がある。前提の誤りを理由に対処ごと捨てない。
- **節を「リモート最終ゲート」の下に置かなかった（#226）**: 事実誤認は第二意見（ローカル事前ゲート配下）でも起きる。あの節の下に置くと片方しか覆えないため、独立した節にして両ゲートから参照する。

### 影響

- **リモート最終ゲートを機構で自動要求している場合、`templates/review-gate.yml` を追加で取り込むこと。** 要求側だけでは今回塞いだ穴は開いたままになる。2 本で 1 組として扱う。
- **`templates/copilot-review.yml` の再取得を推奨。** 失敗時の診断が加わる。要求が成功する環境では挙動は変わらない。
- 規範は追加のみで、既存の記述は変更していない。ファイル名・参照パスも変えていないため、既存の取り込みは壊れない。
- `review-gate.yml` は判定を commit status として出すため、ワークフローに `statuses: write` 権限が要る。要求する権限は `pull-requests: read` に留め、確認側が要求できないことを機構で保証している。

## v0.1.7

### Summary
- **第二意見ゲートが重大な指摘を偽通過させる不具合を修正した**（issue #214）。`templates/gemini-review.sh` の通過判定が、出力全体が `LGTM` 一意であることではなく、装飾を除いて `LGTM` と一致する**行を含むこと**で判定していた。指摘と `LGTM` 行が混在した出力を通していた。
- あわせて、判定の対象をモデルの回答（stdout）だけに限定した。CLI が stderr へ出す警告は回答ではないため、判定へ混ぜない。
- **`@` を含む差分でレビューが実在しない誤りを報告する不具合を修正した**（issue #215）。差分本文を CLI へ直接渡していたため、本文中の `@` がファイル参照として展開され、モデルには壊れたテキストが渡っていた。差分は一時ファイルへ書き、ファイル参照で渡すようにした。
- **挙動変更を含む。** これまで通過していた一部の出力が指摘ありになる。取り込み済みの利用側は雛形を再取得すること。

### Highlights

- **「一意な出力」と「一意な出力を含む」は別（#214）**: `review-workflow.md` は第二意見に「重大な指摘がなければ通過を示す一意な出力を返すこと」を要求している。修正前の実装はモデル出力全体を行単位の一致検査へ流しており、*どれか 1 行*が `LGTM` と一致すれば通過していた。規範が要求する保証になっていない。
- **偽通過は実際に起きる形で起きる（#214）**: ファイル別に講評して途中の 1 行へ `LGTM` と書く形、指摘の末尾へ `**LGTM**` を添える形は、いずれもモデルが自然に取る出力。どちらも修正前は通過し、致命バグの指摘がそのまま push まで通っていた。この 2 形を回帰テストへ加え、修正前の実装で落ちることを実測で確認している。
- **緩める方向は採らない（#214）**: 「一致検査が厳しすぎる」として部分一致へ緩める案は採用していない。緩めると `not LGTM` や `LGTM とは言えない` の類まで通過し、偽の緑がさらに広がる。ローカル事前ゲートは push 前の最後の機械判定であり、ここでの偽の緑は指摘をそのまま通す。
- **判定に stderr を混ぜない（#214）**: 修正前は `2>&1` で stderr を回答へ畳み込んでいた。行の存在で判定している間は無害だったが、出力全体の一意性で判定するとこれが効く。実測で、gemini CLI は端末の色数や ripgrep 不在の警告を stderr へ出す。混ぜたままだと警告 1 行で `LGTM` が指摘ありに化け、ゲートが常に赤くなって無視されるようになる。判定は回答だけで行い、stderr は失敗時の診断へ回す。

- **レビューが「実在しない誤り」を報告していた（#215）**: 差分を CLI へ直接渡すと、本文中の `@` がファイル参照（@ メンション）として展開される。実測では `noreply@github.com` が `noreply @github.com` に、`*@*` の `@*` がリポジトリ内の実在パスに化けた。モデルは壊れた側を読み、実ファイルには存在しない誤りを致命バグとして報告する。報告元では 3 回の実行がすべて同じ幻を報告し、**提示された修正案が実ファイルの現状と 1 文字も違わなかった**。同じ差分なら同じ化け方をするため、多数決でも落とせない。該当するのは `@` を含む差分すべて（メールアドレス、シェルの `${arr[@]}`、デコレータ等）で、日常的に踏む。
- **ファイル参照で渡す（#215）**: 差分を一時ファイルへ書き、`@<パス>` で参照させる。`@` で注入されたファイルの中身は再展開されないため、差分は素通しでモデルへ渡る。一時ディレクトリは `--include-directories` で workspace へ加える（加えないと CLI は応答を返さないまま止まる）。コードブロックで囲む、CLI のフラグで無効化するといった回避策は、いずれも成立しないことを実測で確認している。一時ファイルはレビュー終了時に削除する。

### 影響

- **雛形の再取得が必要**（挙動が変わるため）。取り込み済みの `scripts/gemini-review.sh` は、修正版で置き換えること。
- `@` を含む差分でこれまで出ていた「実在しない指摘」は出なくなる。第二意見の指摘は実ファイルの内容に対応するようになる。
- モデルへ与える権限は変えていない。ツール実行は不要のままで、workspace へ加えるのは差分を書いた一時ディレクトリだけ。
- 置き換え後、これまで緑だった差分が指摘ありになる場合がある。それは修正前に見落としていた指摘であり、内容は出力へそのまま表示される。
- 装飾された `LGTM`（`**LGTM**` / `` `LGTM` `` / `LGTM.` / `LGTM。`）は従来どおり通過する。判定を厳しくした結果ゲートが常に赤くなると無視されるようになるため、装飾の除去は残している。
- 判定ロジック以外のインターフェース（`--range` / `--model` / `--runs`、`GEMINI_REVIEW_RUNS` / `GEMINI_REVIEW_MODEL`、終了コードの意味）は変わっていない。

## v0.1.6

### Summary
- **並列実装後の統合検証を規範化した**（issue #199）。`review-workflow.md` に「並列実装後の統合検証」節を追加し、統合したツリー上で各レーンの受け入れ条件をすべて再実行する工程を定めた。レーン単体の緑は統合後の緑を意味しない。
- `shared-ai-rules.md` 12 章（機構化の判断基準）に「一覧の複製は機械照合で担保する」節を追加した（#199）。既存の「儀式のみを検査できるものは機構化しない」と対になる判断軸。
- 規範の追加のみ。**ファイル名・参照パスは変えていない**ため、既存の取り込みは壊れない。

### Highlights

- **統合パスだけでは漏れる（#199）**: 実測で、8 レーン並列の統合で 3 件、3 レーン並列の統合で 5 件の統合欠陥が出た。いずれもレーン単体の受け入れ検証は緑で、マージの機械的な衝突検査も衝突を報告していない。原因はすべて同一で「**文書が実装の一覧を書き写している**」構造だった。一方のレーンが実装へ項目を足し、他方が同じ一覧を別の理由で書き換えると、どちらのレーンも自分の中では整合しているため単体検証を通過し、編集した行が重ならなければ衝突も出ない。衝突検査が見るのは同じ行を触ったかであって、内容が整合しているかではない。
- **目視の照合を工程にしない（#199）**: 8 レーンの回では、3 件のうち 1 件が統合後の人による目視照合をすり抜け、リモート最終ゲートで初めて検出された。目視を工程に据えると漏れるため、一覧の照合は機械照合で担保し、統合検証はその機械照合を統合ツリー上で再実行する工程として位置づける。
- **統合ツリー側で直す（#199）**: 統合検証で落ちた欠陥はレーンへ差し戻さない。そのレーン単体では再現しないため、差し戻しても修正の妥当性を確認できない。
- **12 章の判断軸（#199）**: 一覧の照合は「更新したか」ではなく「**一致しているか**」を検査する。実質を検査できるので空更新では通過せず、12 章が機構化を禁じる「儀式のみを検査できるもの」には当たらない。機構が一致・不一致の判定そのものを生むため迂回できず、機構化してよい側に入る。実装側から一覧を生成できるなら生成し、できないなら実装の出力と記載を突き合わせて差分で落とす検査を置く。機械照合を置けない一覧は、そもそも複製すべきかを見直す。

### 影響

- 規範の追加のみで、既存記述の削除・改名は伴わない。既存の取り込み（submodule / subtree / 手動同期）はそのまま追随できる。
- 並列実装を行う利用側には、統合後に各レーンの受け入れ条件を再実行する工程が加わる。
- 一覧の照合検査そのものの実装は利用側（プロジェクト層）の責務であり、このパッケージは配布しない。

## v0.1.5

## v0.1.4

### Summary
- 第二意見レビュー雛形 `templates/gemini-review.sh` に複数回実行と多数決を追加した（`GEMINI_REVIEW_RUNS` / `--runs`。既定 1 で従来と同一挙動）。あわせて `review-workflow.md` へ「第二意見の非決定性」節を追加し、1 回の LGTM が不在の証明ではないこと、主レビューを省略してよい根拠にならないことを明記した（issue #157）。既定の挙動を変えないため後方互換。

### Highlights
- **非決定性への対処（#157）**: 第二意見は同じ差分でも実行のたびに結果が変わる。実測で、同一コミットへの 4 回の実行が LGTM 2 回・指摘あり 2 回に分かれた。gemini CLI に temperature / seed に相当するオプションは無く、フラグでは決定化できない。`GEMINI_REVIEW_RUNS` で実行回数を増やし、指摘を報告した実行が**過半数**（`floor(N/2)+1`）に達したときだけ落とす。N=1 なら閾値 1 で従来と同じ。
- **過半数を採る理由**: 「1 回でも指摘があれば落とす」（fail-closed）にすると、誤検出のたびに反証が必要になり、ゲート自体が無視されるようになる。実際にこの規範を運用した一連の作業で、第二意見の指摘の多くが反証された。トレードオフとして**少数回しか現れない指摘は通過する**。この限界は `review-workflow.md` に明記し、第二意見を「補助」と位置づけて受け入れる。
- **少数意見も出力に残す**: 過半数に届かなかった指摘も、どの実行が何を報告したかとともに出力する。集約結果だけを出すと確認すべき指摘が消えるため。
- **不正な回数は fail-closed**: `--runs` が 0・負数・非数値なら、実行前に停止する。黙って既定へ落とすと、増やしたつもりのゲートが実際には効いていない状態になる。あわせて基数を `10#` で固定した。bash の算術評価は先頭 0 を 8 進数として扱うため、固定しないと `08` / `09` は比較自体がエラーになって検証をすり抜け、`010` は 8 と解釈されて「10 回のつもりが 8 回」になる（閾値も狂う）。
- **`.env` からの解決を修正（付随）**: `.env` ローダーの読み込みが `GEMINI_REVIEW_MODEL` / `GEMINI_REVIEW_RUNS` の既定値解決より後にあり、プロジェクト `.env` に書いた値が効かなかった（不正な値も検証をすり抜けた）。ローダーを既定値解決の前へ移し、優先順位を **CLI 引数 > `.env` > 既定** に確定した。`GEMINI_REVIEW_MODEL` は本件以前からの挙動。
- **引数解析の修正（付随）**: 値を伴わないオプション指定（`--range` / `--model` / `--runs` で終わる）が `set -u` 下で `unbound variable` として落ちていた。何が足りないかを示して停止するよう改めた。`--range` / `--model` は本件以前からの挙動で、同じ引数解析部のためまとめて直した。

### 影響
- `GEMINI_REVIEW_RUNS` を設定しなければ、実行回数・出力・終了コードとも従来どおり。
- 回数を増やすと所要時間は回数に比例する。
