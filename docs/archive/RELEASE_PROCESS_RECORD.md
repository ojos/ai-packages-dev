## 発端: 整合性の破壊（実測）

`ojos/devcontainer-bootstrap` v0.2.1 で検証チェーンが切れていた。

| 項目 | 値 |
|---|---|
| `RELEASE-MANIFEST.json` が記録した `SHA256SUMS` のハッシュ | `1ee89327...` |
| 実際に公開されている `SHA256SUMS` のハッシュ | `4edbea2b...` |

マニフェストが**存在しない `SHA256SUMS` を指している**。`audit_release_assets` はこの状態で pass する。
資産の**存在**しか見ておらず、整合性を検証しないため。

**この破壊は現在も公開されたままである**（後述）。

## 原因の構造

3 層になっており、上が下を制約する。

```
C. 公開リポジトリとは何か（成果物置き場か、開発リポジトリか）
   └─ B. どのツールがリリースを所有するか        ← 整合性破壊の原因はここだけ
        └─ A. どこで実行するか（ローカル / CI）
```

- **A だけ直しても解決しない。** `release.yml` はタグ push で発火するため、実行場所を変えても競合は残る。
- **B だけ直せば解決する。** ローカル実行のままでも整合性は回復する。
- **A と B は別事象**であり、絡みは一方向（B が A を制約する）。

### C の決着

**公開リポジトリ = 成果物置き場。開発の関心事を置かない。**

これは新しい設計ではなく、このプロジェクトが元から持っていた原則（開発用リポジトリと配布用リポジトリを役割で分ける）である。

破壊の原因は、その原則を破ったことだった。`release.yml`（コードを検査してビルドする **開発の関心事**）を成果物置き場に置いたため、公開リポジトリが「半分は成果物置き場、半分は開発リポジトリ」という中途半端な状態になり、モノレポ側のツールと同じ仕事を始めて衝突した。

原則を貫くと判断が機械的になる。

| 置いてよい | 置いてはいけない |
|---|---|
| 配布物（`bootstrap.sh` / `doctor.sh` / `README.md`） | CI / workflow |
| リリースと資産 | ビルドロジック、テスト |

「公開リポジトリにテストを置いてゲートを強くする」は原則違反であり、正しくはモノレポ側の preflight で通す。

## 消費モデル（設計の起点）

| パッケージ | 実体 | リリースの本体 | ミラーの要否 |
|---|---|---|---|
| DCB | curl して実行する単一スクリプト | **リリース資産**が load-bearing | 役割分離による**選択**。技術的にはモノレポからでも配れる |
| dotfiles | 文書のみ。ランタイムなし | **git タグ**が本体 | **構造的に必須**。submodule / subtree はリポジトリのルート単位でしか動かない |

- DCB の README は `curl` + `sha256sum -c` を指示する。
- dotfiles の README は submodule / subtree / 手動同期でタグ + SHA を固定すると定める。資産をダウンロードしない。
- DCB の `--dotfiles-from` が使うのは git 自動生成の `archive/refs/tags/vX.tar.gz` であり、リリース資産ではない。

**dotfiles の 3 資産は誰も消費していない。**

## 訂正: 誤っていた分析

将来の判断を誤らせないため、明示的に記録する。

| 当初の分析 | 実際 |
|---|---|
| **「ミラーが存在する唯一の理由は、モノレポが private だから」** | **誤り。** 理由は役割分離（開発用と配布用を分ける）。private/public は直交する |
| **「モノレポを public にすればミラー機構ごと不要になる」** | **誤り。** dotfiles のミラーは submodule 粒度のため構造的に必須。public 化で消えるのは DCB のミラーの「理由」だけ |
| 「public 化すれば CI から PAT なしでリリースできる」 | **誤り。** ミラーが残る限りクロスリポジトリ push が必要で、PAT は要る |
| 「レースが偶然ユーザーを救っていた」 | **誤り。** 実測すると両方の理論で documented な手順は失敗していた。レースが分けたのは失敗の度合いだけ |
| 「C は未決」 | **誤り。** プロジェクトの原則が既に答えを持っていた |
| `RELEASE_ASSET_STANDARDIZATION_PROPOSAL` を「Phase 1〜3 実装済み」として削除 | **実装されたことと正しいことを取り違えていた。** 3 パッケージへ一律 3 資産を課す均一化であり、各パッケージが何を必要とするかを問うていない |

public 化に実質的な意味があるとすれば、アーキテクチャではなく**受け口**（利用者が issue を立てる場所）の観点。
現在、公開リポジトリは両方とも issues が有効だが、開発は private のモノレポで行われている。
利用者が見つける場所と、作業が行われる場所が食い違っている。

## 実施内容

### 1. 二重所有の解消（`ead8083`）

- パッケージから `release.yml` を削除。公開リポジトリへ二度と渡らない
- `SHA256SUMS` の対象を `SUMS_TARGETS` として呼び出し側で宣言。DCB は `bootstrap.sh` と `doctor.sh`
- README の手順を対象と一致させた（`doctor.sh` も取得する）
- 契約をテストで固定

`release.yml` が担っていた機能の行き先:

| 機能 | 移動先 |
|---|---|
| `bash -n` / shellcheck | モノレポ CI（`.github/workflows/ci.yml`） |
| SHA256SUMS 生成・リリース作成 | `release-packages.sh` |
| 機能テスト | **元から無かった**（これが v0.2.0 を通した）。現在は preflight が実施 |

### 2. パッケージ単位のリリースと不変性（`0a94455`）

2 つの設計問題があった。

1. `--dcb-version` と `--dotfiles-version` が両方必須で、片方だけリリースできない
2. 既存タグを再指定すると `--clobber` で資産が差し替わる。タグは動かないのに中身だけが変わる

組み合わさって実害が出ていた。DCB v0.2.1 を出す際に `--dotfiles-version v0.3.0` を強制的に渡した結果、
**公開済みの dotfiles v0.3.0 の資産が 13:34 作成 → 13:38 上書きと、4 分間で 2 回書き換わった**。

対処:

- パッケージごとに独立してリリース可能に。`--owner` は必須、版は最低 1 つ
- `require_version_unpublished` を preflight へ。副作用の前に止める（`init_and_push_release_repo` が公開 main を全置換した後では手遅れ）
- `tag_and_release` の `--clobber` 経路を除去し、新規作成のみへ縮退
- 検査を安い順に並べた。版の重複は問い合わせ 1 回で分かるため、テスト実行より先に判定する

### 3. テスト

`packages/devcontainer-bootstrap/tests/` に 67 件 / 6 ファイル。うちリリース契約が 16 件。

`gh` と `git status` をスタブ化し、実トークンにも公開リポジトリにも触れずに検証する。
「公開済みなら副作用ゼロで止まる」は、`gh` へ `release view` 以外が呼ばれたら失敗する形で確認している。

すべて**変異を注入して検出を確認済み**。

## 実装中に判明した事実

| 事実 | 影響 |
|---|---|
| `PACKAGE_ARCHIVE.tar.gz` は同内容でもハッシュが毎回変わる（tar のタイムスタンプ） | 「内容が同じなら上書きしてよい」という冪等判定が成立しない。上書きは常に別物への差し替えになる |
| 版の重複判定を `run_dcb_tests` の後に置くと**無限再帰**する | テストが release-packages.sh を呼び、その preflight がテスト一式を再起動する。実際にハングし 10 個の run-tests.sh が並走した。安い検査を先に置くという原則が、偶然この問題も解いた |
| 公開リポジトリには `tests/` も規範ソースも渡らない | 公開側で機能テストを実行できない。リリース前の preflight が唯一のゲート |

## 残る問題

### 実害があるもの

| 問題 | 状態 |
|---|---|
| **公開中の v0.2.1 の整合性が壊れている** | マニフェストが存在しない SHA256SUMS を指す。README の手順も失敗する。**次回リリースまで解消しない** |
| **公開側に `release.yml` が残存**（sha=9c1a2c6） | 次回リリース時に `init_and_push_release_repo` が `.git` 以外を全置換するため自然に消えるが、それまではタグ push で発火しうる |
| **dotfiles の `templates/` が未公開** | 案 A で追加した雛形が公開版に無いため、README が案内する導入手順が実行できない |

### 未決の論点

| 論点 | 内容 |
|---|---|
| **dotfiles の資産の要否** | 誰も消費していない。タグのみで足りる可能性。決めれば `PACKAGE_ARCHIVE` の再現性問題ごと消える |
| **均一化の撤回** | パッケージごとに消費モデルが異なるのに同じ形（3 資産）を課している |
| **audit の検証内容** | 存在確認から整合性検証へ。現状は儀式を検査しており、`shared-ai-rules.md` の「機構化の判断基準」が禁じる形 |
| **A: 実行場所** | モノレポ CI へ移すか。ローカル実行は今回 403 と壊れた python で実際に事故を起こした。ただしクロスリポジトリ push 用の PAT または GitHub App が要る。全置換は破壊的なため、トリガー設計（タグ push か workflow_dispatch か、承認を挟むか）も要判断 |
| **利用者の受け口** | 公開リポジトリは issues が有効だが誰もいない。開発は private のモノレポ |
| **`PACKAGE_ARCHIVE` の再現可能化** | `--mtime` / `--sort=name` / `--numeric-owner` 等。ただし資産の要否が決まれば不要になる可能性 |
