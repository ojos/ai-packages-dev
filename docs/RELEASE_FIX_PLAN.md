リリースを**パッケージ単位で独立して行える**ようにし、**公開済みリリースの不変性**を回復する。

## タスク

### T1: パッケージ単位のリリースを可能にする

- **責務**: 引数仕様と実行ブロックを、指定されたパッケージだけを対象にする形へ変える
- **前提**: なし
- **内容**:
  - `--dcb-version` / `--dotfiles-version` を任意にし、**最低 1 つ**を要求する
  - preflight の検証（`validate_dcb_docs` 等）を、対象パッケージのみに適用する
  - 実行ブロックを対象パッケージのみに適用する
  - usage を更新する
- **検証**: A1 / A2 / A3
- **担当候補**: 自実装（単一ファイル・構造変更）

### T2: 公開済みバージョンへの上書きを禁じる

- **責務**: 版の重複を preflight で検出し、副作用が出る前に止める
- **前提**: **T1 に依存**。「どのパッケージを対象にするか」の構造が定まらないと、検査対象を決められない
- **内容**:
  - preflight に「指定タグの release が公開側に既に存在しないこと」の検証を追加する
  - 存在する場合は、`prepare_*` / `init_and_push` へ進む前に失敗させる
  - `tag_and_release` の `--clobber` / `edit` 経路を、新規作成のみへ縮退させる
- **検証**: A4 / A5
- **担当候補**: 自実装

### T3: 回帰を防ぐテスト

- **責務**: T1・T2 の振る舞いをテストで固定する
- **前提**: **T1・T2 に依存**（振る舞いが確定してから書く）
- **内容**:
  - `tests/test-release-contract.sh` へ追加する
  - ネットワークと実トークンに依存しない形にする（`gh` を呼ぶ経路はスタブ化するか、引数検証層のみを対象にする）
  - **変異を注入して検出を確認する**
- **検証**: A6
- **担当候補**: 自実装

### T4: 手順書の更新

- **責務**: `RELEASE_EXECUTION_RUNBOOK.md` を新しい引数仕様へ合わせる
- **前提**: **T1 に依存**（仕様が確定してから書く）
- **内容**: 実行例をパッケージ単位へ。既存版の再公開が失敗することを明記
- **検証**: CI のリンク検査、および手順どおりに実行できること
- **担当候補**: 自実装

## 依存順と並列化

```
T1 ──> T2 ──> T3
  └──> T4
```

- **T1 → T2**: 必須。T2 の検査対象は T1 が定める構造に従う。逆順だと T2 を書き直すことになる
- **T1・T2 → T3**: 必須。振る舞いが確定する前にテストを書くと、テストが仕様を先取りして固定してしまう
- **T1 → T4**: 必須。仕様が確定してから手順を書く

**並列実行できるのは T2 と T4 のみ**（どちらも T1 のみに依存し、互いに独立。触るファイルも異なる）。

ただし **T2 と T4 の作業量はどちらも小さく、並列化の利得は分離コストを下回る**と判断する。
`isolation: "worktree"` を用いた並列委譲は行わず、逐次で実施する。

**T1 → T2 → T3 は本質的に直列**であり、これを並列化する余地はない。作業量の多寡ではなく依存関係による判断。

## スコープ外だが記録すべき問題

### PACKAGE_ARCHIVE の再現不可能性

同じ内容から生成しても、`tar` がタイムスタンプを埋めるためハッシュが毎回変わる。

- 影響: 「再実行しても同じ成果物になる」ことを保証できない
- 本計画では、上書き自体を禁じることで**回避**する（再現性がなくても、上書きしなければ問題は顕在化しない）
- 恒久対処には `--mtime` / `--sort=name` / `--numeric-owner` 等による再現可能アーカイブ化が要る
- **そもそも `PACKAGE_ARCHIVE.tar.gz` を誰も消費していない**（RELEASE_PROCESS_REVIEW 参照）。
  資産の要否を決めれば、この問題ごと消える可能性がある

### 失敗後の再試行手段

上書きを禁じると、リリースが途中で失敗した場合の再試行ができなくなる。

- npm や crates.io と同様、公開済みバージョンの再公開を禁じるのが一般的
- 再試行するなら、公開側の release を手で削除するか、版を上げる
- 本計画では**明示的なエラーメッセージで再試行手段を案内する**に留める

本計画の完了により、**論点 A（モノレポ Actions でのリリース）に安全に着手できる**。
現状のまま CI 化すると、上書きの危険を抱えたまま自動化することになる。
