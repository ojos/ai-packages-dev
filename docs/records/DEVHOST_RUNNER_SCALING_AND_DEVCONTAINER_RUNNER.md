## 前提: 今の自前のランナーの作り

- `dev-runner@<名前>.service` が `dev runner run <名前>` を起こし、`--ephemeral` のランナーを `--rm` のコンテナで動かす。ジョブを 1 つ終えるとコンテナが抜け、`Restart=always` が新しいコンテナで起こし直す。ジョブごとにまっさらな環境になる。
- 登録先はリポジトリ単位ではなく組織単位。組織名・ラベルなどの固有の値は外部の機械の設定ファイル（`~/.config/dev/runners`）に置き、配布物には書かない。
- 並列数は、`runners` に行を足し、ユニットを名前ごとに有効にして増やす。
- Docker のソケットは `docker=yes` にしたランナーにだけ渡す。
- パッケージに機能があることと、外部の機械で動いていることは別。動かすには `install.sh` → `runners` の記入 → PAT の配置（権限 600） → `dev runner build` → `systemctl --user enable --now dev-runner@<名前>.service` を手で行う。動作の確認は `dev doctor --runner <名前>` と、GitHub の組織の Settings → Actions → Runners。

## 1. オートスケーリングとキューイング

### キューイング: 作る必要が無い

GitHub 側がもともと持っている。ジョブは、ラベルが合う空いたランナーが現れるまで GitHub 上で待つ（最大 24 時間）。今の作りでもランナーは 1 ジョブごとに起こし直されるので、1 台でもジョブは順に処理される。こちらで待ち行列を作る必要は無い。

### オートスケーリング: 作れるが、機械 1 台では利得が小さい

| 方式 | 難しさ | 中身 |
|---|---|---|
| A. 固定の台数を増やす | ほぼゼロ（今の機能で使える） | `runners` に行を足し、`dev-runner@runner2` などを有効にする。待機中のランナーは接続を張って待つだけで、資源をほとんど使わない |
| B. ポーリングで増減する | 中 | `dev` に、待っているジョブの数を API で数えて上限までコンテナを起こす処理を足す |
| C. Webhook で増やす | 中〜高 | `workflow_job` の `queued` の通知を受けてコンテナを起こす |
| D. 公式の仕組み | 高 | Kubernetes の上で Actions Runner Controller（ARC）を動かす |

B〜D の注意点:

- **B**: 組織全体の待ちジョブを一度に数える API が無く、リポジトリごとに数えて回ることになる。回数制限に当たりやすく、PAT にリポジトリの Actions を読む権限を足すことになる（今の PAT は組織の「Self-hosted runners: Read and write」だけ）。遅れて反応するため、増やしすぎ・増やし足りないが起きる。
- **C**: 外から届く受け口が要る（Cloudflare Tunnel などで公開する）。通知の署名の検証と、取りこぼしへの備えも要る。外部の機械に公開の受け口を開けることになり、守る範囲が広がる。
- **D**: 機械 1 台のために Kubernetes を入れるのは重い。GitHub は Kubernetes を使わずに自前のスケーラーを組むための部品も出していたはずだが、未確認。

機械 1 台では、増やせる上限はその機械の CPU とメモリで決まる。待機中のランナーはほぼ資源を使わないので、上限の台数をはじめから常駐させる A と、B・C の違いは小さい。違いが出るのは、待機中のランナーの台数そのものを減らしたいときと、機械が複数台あってどこで起こすかを選ぶときだけ。

### 結論

1. まず A で 2〜3 台に増やし、待ちの出方を見る。
2. 同時に走る重いジョブで機械が詰まるなら、コンテナに CPU とメモリの上限（`--cpus` と `--memory`）を付ける機能を足す。小さな変更で済む。
3. B 以降は、機械が 2 台以上になったとき、または待機中のランナーの台数を減らす必要が出たときに検討する。

## 2. devcontainer をランナーとして動かす（見送り）

### 考えていた使い方

devcontainer の認証情報（`codex` / `agy` の OAuth のログイン状態）を使い、第二意見のレビューをランナー上で行う。

### 技術的には作れる

1. **devcontainer の中でランナーを動かす**: devcontainer に公式のランナーを入れて登録し、常駐させる。`~/.codex` / `~/.gemini` のログイン状態がそのまま使える。
2. **devhost のランナーのコンテナへ、ログイン状態の volume を渡す**: `dev runner run` に `codex-storage` / `gemini-storage` を取り付ける設定を足す。今の使い捨ての作りに近いのはこちら。

どちらも実装の難しさは低い。

### 見送った理由

- **そのランナーで走るジョブは、どれも認証情報を読める。** ワークフローを書き換えた PR のブランチも、同じランナーグループを使う他のリポジトリも読める。ランナーを使い捨てにしているのは、ジョブ間に状態を残さないためで、認証情報を取り付けるとその狙いが崩れる。
- **このリポジトリの方針と食い違う。** `.github/project-ai-rules.md`「第二意見（クロスモデル）」は、`codex` / `agy` について資格情報をコンテナの外から注入する経路を持たないとしている。volume をランナーへ渡すことは、その経路を新しく作ることになる。
- **同じログインを 2 か所で使うと、片方が切れるおそれがある**（未確認）。OAuth の更新トークンが使うたびに入れ替わる方式なら、devcontainer とランナーが別々に更新したときに片方のログインが失効しうる。gh の OAuth App の上限枠（`.github/project-ai-rules.md`「GitHub 認証（gh CLI）」）と似た連鎖が起きる余地がある。
- **利用規約**（未確認）。ChatGPT や Google アカウントの OAuth のログインを CI の自動実行に使うことが規約上許されるかを確かめていない。

### この使い方で得られたはずのもの

第二意見を著者の手元ではなくランナーで取れば、レビューの内容が著者を通らなくなる。リモート最終ゲートを置かないと決めたときに諦めた性質（`.ai-playbook/review-workflow.md`「リモート最終ゲート（任意の層）」）の一部が戻る。ただし、記録の投稿や起動が著者の操作のままなら、戻る性質は限られる。

### 再検討するときの形

- **API キーで動くエンジンを使う**のが素直。`gemini` の `GEMINI_API_KEY` を Actions の secret に置き、普通のジョブで第二意見を取る。ログイン状態を持ち出さずに済み、ランナーは GitHub のものでも自前のものでもよい。
- **OAuth で動くエンジンをどうしても使う**なら、少なくとも次を揃える。先に、上の方針（OAuth の認証情報をランナーへ持ち出すか）を変えるかどうかの判断が要る。
  - 専用のラベルとランナーグループを用意し、使えるリポジトリを絞る
  - 起動を `workflow_dispatch` などの信頼できる操作に限り、PR のブランチのワークフローでは走らせない
  - devcontainer とは別のアカウント（または別のログイン）を使い、同じログインを 2 か所で使わない
